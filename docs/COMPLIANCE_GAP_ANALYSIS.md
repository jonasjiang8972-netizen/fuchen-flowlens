# 拂尘 FlowLens 等保三级与金融行业合规差距评估

> 评估对象：`claude/intelligent-archimedes-ug4830` 分支当前代码（v0.6.0 + 后续安全修复）
> 评估日期：2026-09-25
> 评估方式：代码审查 + 本地运行验证 + 依赖漏洞扫描
>
> **更新（v0.7.0）：** 已按第 6 节路线完成大部分 P0 整改，并拆分出系统管理后台，整改状态见第 8 节。第 0–7 节保留评估时的原始结论。

## 0. 结论

**当前产品不满足等保三级要求，也不满足金融行业附加要求，暂不具备进入金融客户等保测评的条件。**

主要原因有五个，任何一个都会导致测评不通过：

1. **数据只存在内存里。** 平台重启后，审计日志、告警、资产全部丢失，无法做到日志留存六个月、数据备份与恢复。
2. **没有传输加密。** 平台只提供 HTTP，前端 nginx 只监听 80 端口。Agent 上报的流量里含有请求头和请求体（可能包含密码、token、身份证号、银行卡号），会以明文传输。
3. **没有使用商用密码。** 身份鉴别、通信、存储都没有使用 SM2/SM3/SM4，不满足 GB/T 39786-2021 三级和金融行业的密评要求。
4. **权限体系不成立。** 除审计日志外，所有接口对任何已登录用户开放；`super_admin` 可以绕过所有角色检查，做不到"三权分立"。
5. **身份鉴别薄弱。** 没有登录失败锁定、没有双因素认证、没有口令复杂度策略、没有会话空闲超时，也没有用户管理功能。

已经具备的基础：口令用 bcrypt 存储；JWT 密钥可配置、只接受 HS256；Agent 使用独立 token 认证，未配置时拒绝访问；CORS 已限制；有审计中间件和角色模型的雏形；平台不持久化请求体原文。

### 重要说明

- 本报告是基于代码的**差距评估**，不是等保测评结论。正式结论只能由具备资质的测评机构出具。
- 等保测评的对象是**部署后的整个信息系统**，包括物理环境、网络架构、安全管理制度和人员管理等。本报告只评估产品软件本身能否支撑这些要求，对应的是 GB/T 22239-2019 中"安全计算环境""安全通信网络""安全管理中心"里与应用相关的条款。
- 金融行业标准的具体数值要求（如口令长度、更换周期）以标准原文和客户的内部制度为准。报告中给出的数值是常见做法，落地前需要与客户确认。

## 2. 总体结果

| 控制类 | 结果 | 高风险差距 |
|--------|------|-----------|
| 身份鉴别 | ❌ 不符合 | 无登录失败处理、无双因素、无口令策略 |
| 访问控制 | ❌ 不符合 | 写操作无权限控制、超级管理员绕过、无用户管理 |
| 安全审计 | ❌ 不符合 | 审计记录内存存储、缺少关键字段、登录不审计 |
| 入侵防范 | ⚠️ 部分符合 | 3 个中危依赖漏洞、无请求体大小限制、容器以 root 运行 |
| 数据完整性 | ❌ 不符合 | 传输和存储均无完整性保护 |
| 数据保密性 | ❌ 不符合 | 无 TLS、无存储加密 |
| 数据备份恢复 | ❌ 不符合 | 仅内存存储 |
| 剩余信息保护 | ⚠️ 部分符合 | 退出不作废 token，token 存在 localStorage |
| 个人信息保护 | ❌ 不符合 | Agent 采集敏感头和请求体且不脱敏、界面无脱敏 |
| 通信传输 | ❌ 不符合 | 平台、前端、Agent 通道均为明文 |
| 安全管理中心（三权分立） | ❌ 不符合 | 角色定义了但没有执行 |
| 商用密码应用 | ❌ 不符合 | 未使用 SM2/SM3/SM4 |
| 恶意代码防范、可信验证 | — 不适用 | 由部署环境（主机、容器平台）满足 |

## 3. 等保三级逐项差距（GB/T 22239-2019 第三级）

风险等级：**高**（测评一票否决或高风险项）/ **中** / **低**。

### 3.1 身份鉴别（8.1.4.1）

| 条款要求 | 现状与证据 | 风险 | 整改建议 |
|----------|-----------|------|----------|
| a) 用户身份唯一标识；口令有复杂度要求并定期更换 | 用户名唯一。没有口令复杂度校验、没有更换周期，也没有修改口令的接口。两个内置账号 `admin` 和 `sec-ops` 共用同一个口令（`platform/internal/storage/mem_store.go` `seedUsers`） | 高 | 增加口令策略：至少 8 位，包含大小写字母、数字、特殊字符中的三类，不能与用户名相同，90 天强制更换，不能与最近 5 次相同。首次登录强制修改初始口令 |
| b) 登录失败处理：限制非法登录次数、超时自动退出 | 登录接口没有失败计数、锁定或限速（`platform/internal/server/server.go` `LoginHandler`）。JWT 固定 24 小时有效，没有空闲超时（`platform/internal/auth/jwt.go:51`） | 高 | 连续 5 次失败锁定账号 30 分钟，同时按 IP 限速。会话空闲 15 分钟自动退出，绝对有效期缩短到 8 小时，支持 token 续期 |
| c) 远程管理时防止鉴别信息被窃听 | 平台只监听 HTTP（`platform/cmd/main.go:85`），nginx 只监听 80 端口（`web/nginx.conf:2`）。用户名和口令明文传输 | 高 | 全链路 HTTPS，见 3.8 节 |
| d) 采用口令、密码技术、生物技术等两种或以上组合的鉴别技术，其中一种至少使用密码技术 | 只有用户名加口令一种方式 | 高 | 增加第二因素：TOTP 动态口令、短信验证码或 USB Key/数字证书。金融客户通常要求支持国密 USB Key（SM2 证书）登录 |

### 3.2 访问控制（8.1.4.2）

| 条款要求 | 现状与证据 | 风险 | 整改建议 |
|----------|-----------|------|----------|
| a) 为登录用户分配账户和权限 | 定义了 `super_admin`、`security_admin`、`auditor` 等角色，但只有 `/audit-logs` 一个接口检查角色（`platform/cmd/main.go:167`） | 高 | 为每个接口定义所需权限，按角色授权 |
| b) 重命名或删除默认账户，修改默认口令 | 内置账号固定为 `admin`/`sec-ops`。未设置 `FLOWLENS_ADMIN_PASSWORD` 时使用默认口令 `admin123`（启动时有警告） | 高 | 首次部署时由安装程序生成随机初始口令并强制修改；支持重命名或禁用内置账号 |
| c) 及时删除或停用多余、过期账户，避免共享账户 | 没有用户管理功能：不能新建、禁用、删除账号，也不能查看账号最后登录时间 | 高 | 增加用户管理：增删改、启停用、90 天未登录自动停用、账号有效期 |
| d) 授予管理用户所需最小权限，实现管理用户的权限分离 | 规则修改（`main.go:158`）、告警处置/封禁（`main.go:147`）、资产认领（`main.go:142`）对任何已登录用户开放，包括只读用户。`super_admin` 绕过所有角色检查（`jwt.go:108`） | 高 | 按最小权限重新设计权限矩阵（见第 5 节），取消超级管理员对审计功能的访问 |
| e)–f) 由授权主体配置访问控制策略；粒度达到主体为用户级、客体为文件或数据库表级 | 没有权限配置界面；数据没有按租户或资产范围隔离，所有用户看到全部数据 | 中 | 支持按业务线、资产分组授权；多租户数据隔离 |
| g) 对重要主体和客体设置安全标记 | 未实现 | 低 | 可结合数据分级结果给资产打标签，按标签控制访问 |

**另外发现的问题：** 告警处置接口接受任意动作名，并且总是返回"执行成功"（`platform/internal/service/alert_service.go:402`），没有真正对接封禁或限流系统。对金融客户来说，这会让处置记录失真，需要校验动作类型并如实记录执行结果。

### 3.3 安全审计（8.1.4.3）

| 条款要求 | 现状与证据 | 风险 | 整改建议 |
|----------|-----------|------|----------|
| a) 启用安全审计，覆盖到每个用户，对重要用户行为和重要安全事件审计 | 有审计中间件，但**登录成功和失败都不记录**（`platform/internal/middleware/audit.go:27` 跳过了登录接口，而且登录接口本身不经过该中间件）。Agent 注册不记录。演示模式下审计完全关闭 | 高 | 必须记录：登录成功/失败、退出、口令修改、用户和权限变更、规则变更、告警处置、配置变更、审计日志查询与导出、Agent 注册 |
| b) 审计记录包括日期和时间、用户、事件类型、事件是否成功及其他相关信息 | 记录了时间、用户名、方法和路径。**缺少源 IP、事件类型、明确的成功/失败字段、操作对象和变更前后内容** | 高 | 结构化审计记录：时间、用户、角色、源 IP、事件类型、操作对象、结果、失败原因、变更前后值 |
| c) 对审计记录进行保护，定期备份，避免受到未预期的删除、修改或覆盖 | 审计日志只存在内存里，平台重启即丢失（`platform/internal/storage/store.go:76` 总是返回内存存储）。没有防篡改措施。另外 `ListAuditLogs` 返回的是最早的 N 条，而不是最新的（`mem_store.go:201`） | 高 | 审计日志持久化到数据库，只允许追加；每条记录用 SM3 做哈希链防篡改；定期备份；支持通过 syslog 发送到客户的 SOC/SIEM。**按《网络安全法》至少留存六个月**，金融客户通常要求更久 |
| d) 对审计进程进行保护，防止未经授权的中断 | 审计写入是异步的，失败会被静默忽略（`audit.go:32`） | 中 | 审计写入失败时告警；关键操作在审计记录写入成功后才执行 |

### 3.7 剩余信息保护与个人信息保护（8.1.4.10、8.1.4.11）

| 条款要求 | 现状与证据 | 风险 | 整改建议 |
|----------|-----------|------|----------|
| 鉴别信息所在存储空间被释放或重新分配前得到完全清除 | 退出登录只是清除浏览器的 localStorage，token 在 24 小时内仍然有效 | 中 | 服务端维护 token 黑名单或会话表，退出时作废 |
| 仅采集和保存业务必需的用户个人信息 | Agent 默认采集全部请求头和请求体（`agent/internal/config/config.go:117-118`），包括 `Authorization`、`Cookie`、登录口令、银行卡号等，并且**不做任何脱敏**就发送给平台（`agent/internal/normalizer/normalizer.go` 只做了长度截断） | 高 | 在 Agent 端脱敏：丢弃 `Authorization`、`Cookie`、`Set-Cookie` 等鉴别头；对口令字段直接丢弃，对身份证、手机号、银行卡号做掩码；只上报检测需要的特征 |
| 禁止未授权访问和非法使用用户个人信息 | 所有已登录用户都能看到全部资产、告警和路径样本；资产的原始路径样本可能含有用户标识（`PathRawSamples`） | 高 | 按权限控制敏感数据可见范围；界面默认脱敏展示，查看明文需要单独授权并记录审计 |

### 3.8 安全通信网络——通信传输（8.1.2.2）

| 链路 | 现状 | 整改建议 |
|------|------|----------|
| 浏览器 → nginx | HTTP 80 端口 | HTTPS，支持国密 TLS（TLCP，SM2/SM4），同时兼容国际算法；开启 HSTS |
| nginx → 平台 | HTTP | 内网也建议启用 TLS，至少限制在隔离网段 |
| Agent → 平台 | HTTP（平台不提供 HTTPS）；共享 token 认证 | 双向 TLS（mTLS），每个 Agent 使用独立证书，替代共享 token；支持国密证书 |

### 3.9 安全管理中心（8.1.5）

三级要求把系统管理员、审计管理员、安全管理员三类角色分开（常说的"三权分立"），并且互相制约。

| 条款要求 | 现状 | 风险 | 整改建议 |
|----------|------|------|----------|
| 8.1.5.1 系统管理：对系统管理员进行身份鉴别，只允许其通过特定命令或界面进行系统管理操作，并对这些操作审计 | 没有独立的系统管理员角色 | 高 | 系统管理员：负责用户、配置、Agent 管理；不能查看或删除审计日志，不能修改检测规则 |
| 8.1.5.2 审计管理：审计管理员只能进行审计分析 | `auditor` 角色存在，但 `super_admin` 也能看审计日志 | 高 | 审计管理员：只能查询、分析、导出审计日志，不能做其他任何操作 |
| 8.1.5.3 安全管理：安全管理员配置安全策略 | `security_admin` 存在，但所有用户都能改规则 | 高 | 安全管理员：负责检测规则、告警处置、数据分级策略 |
| 8.1.5.4 集中管控 | 平台本身就是集中监测平台；但自身的审计和告警不能对外输出 | 中 | 支持通过 syslog/Kafka 把自身审计日志和告警发送到客户的 SOC/SIEM；提供时间同步（NTP）配置说明 |

## 4. 金融行业附加要求

### 4.1 商用密码应用（GB/T 39786-2021 三级，金融行业"密评"）

| 层面 | 三级要求 | 现状 | 风险 |
|------|---------|------|------|
| 身份鉴别 | 采用密码技术对登录用户进行身份鉴别 | 口令 + bcrypt，未使用商用密码 | 高 |
| 通信 | 采用密码技术保证通信实体身份真实性、数据保密性和完整性 | 无 TLS | 高 |
| 存储 | 采用密码技术保证重要数据存储的保密性和完整性 | 无持久化，无加密 | 高 |
| 访问控制信息和日志完整性 | 采用密码技术保证完整性 | 无 | 高 |

整改方向：
- **通信：** 国密 TLS（TLCP），可基于 Tongsuo（铜锁）或 GmSSL。
- **身份鉴别：** 支持 SM2 证书或 USB Key 登录。
- **口令存储：** 改用 SM3 加盐的慢哈希方案，或在客户接受的前提下保留 bcrypt 并用 SM4 加密存储。
- **数据：** SM4 存储加密，SM3-HMAC 做完整性校验；JWT 签名改为 SM2 或 SM3-HMAC。
- **密码产品：** 密钥管理对接客户的密码机或 KMS，使用的密码模块需要具备商用密码产品认证。

### 4.2 个人金融信息保护（JR/T 0171-2020）

产品要旁路采集金融业务流量，流量里天然包含大量个人金融信息，这是金融客户最关注的点。

| 要求 | 现状 | 风险 | 整改建议 |
|------|------|------|----------|
| C3 类信息（口令、支付密码、卡片验证码等鉴别信息）原则上不应留存 | Agent 采集并上报完整请求头和请求体，包括口令和 token | 高 | Agent 端直接丢弃 C3 类信息，平台端再做一次兜底过滤 |
| C2 类信息（身份证号、银行卡号、手机号等）传输和存储要加密，展示要屏蔽 | 明文传输；界面没有统一的脱敏展示组件 | 高 | 传输加密；存储加密；界面默认掩码（如 `6222 **** **** 1234`、`110***********1234`） |
| 按数据类别区分访问权限，访问留痕 | 无数据级权限控制，查看敏感数据不记录审计 | 高 | 明文查看需要单独授权，每次查看都记录审计 |
| 数据最小化采集 | 默认全量采集请求体 | 中 | 默认只采集元数据和检测特征；请求体采集需要客户显式开启，并限定到指定接口 |

### 4.3 金融数据分级与生命周期（JR/T 0197-2020、JR/T 0223-2021）

| 要求 | 现状 | 整改建议 |
|------|------|----------|
| 按金融数据分级指南识别和标记数据级别 | 有敏感字段识别（`classifySensitiveFields`），但分类是自定义的，没有对应到 JR/T 0197 的 1–5 级 | 分级规则对齐 JR/T 0197，资产和字段标注数据级别 |
| 数据采集、传输、存储、使用、删除全生命周期保护 | 没有数据保留期限和到期删除机制 | 支持按数据级别配置保留期，到期自动删除并记录 |
| 数据本地化 | 私有化部署，数据不出客户环境；但 `README` 中的技术栈规划提到的组件需确认都可以本地部署 | 在交付文档中明确数据存储位置和不出境承诺 |

### 4.4 金融行业等保实施指引（JR/T 0071-2020）的常见加强项

以下是金融机构在三级基础上通常会额外检查的内容，具体数值以客户制度为准：

- **口令：** 长度和复杂度要求更严格，定期强制更换，禁止使用历史口令。
- **会话：** 空闲超时时间更短，限制同一账号并发登录。
- **审计：** 日志留存时间更长，审计日志要能对接行内安全运营平台。
- **运维：** 管理操作通过堡垒机进行，限制管理终端来源 IP。
- **供应链：** 提供软件物料清单（SBOM）、第三方组件漏洞扫描报告和源代码安全审计报告。

### 4.5 产品准入

FlowLens 本身是网络安全产品。进入金融客户采购前，需要确认它是否属于《网络关键设备和网络安全专用产品目录》范围；如果属于，需要取得相应的安全认证或检测。另外，金融客户普遍要求提供第三方渗透测试报告和源代码审计报告。

## 6. 整改路线

### P0：进入测评的前提（预计 4–6 周）

### 系统管理后台拆分

与 API 安全无关的平台管理能力已统一移到新的系统管理后台（`/api/v1/admin/*`，前端独立控制台）：

- **系统管理员：** 用户管理、角色与权限、安全策略、采集器管理、系统设置。

API 安全管理平台只保留 API 安全侧的操作和策略配置：资产、告警与处置、检测策略、调用链路、数据治理、覆盖率等。API 安全侧只能看到采集覆盖的汇总数据，看不到采集器管理功能。
