# 数据库查询性能：TB 级数据 2 秒内响应

> 适用版本：v0.7.0 之后（分区表 + 组合索引）
> 测试日期：2026-09-25
> 复现工具：`platform/tools/dbbench`

## 1. 结论

**管理后台的全部查询在 TB 级数据下可以在 2 秒内返回，前提是使用 SSD 并按第 6 节配置。**

- **实测：** 3000 万条审计日志（17.9GB）、**完全冷缓存**（重启数据库并清空操作系统页缓存），所有查询首次执行都不超过 12.4 毫秒。
- **与数据量无关：** 数据量从 1000 万增加到 3000 万（每天的数据密度变为 3 倍），查询耗时基本不变。
- **推算：** 每个查询读取的页数有固定上限（计数不超过约 100 页、列表不超过约 60 页），只会随 B 树层数缓慢增加。推算到 1TB（约 17 亿行），冷缓存最坏读取约 180 页，SSD 上约 20～40 毫秒。

**没有实际测试 1TB 数据。** 测试环境只有约 28GB 磁盘。TB 级的结论来自第 4 节的读页数模型，以及"数据量翻 3 倍、耗时不变"的实测。

以下操作的耗时与数据量成正比，**做不到 2 秒**，已改为其他方式处理（见第 5 节）：

- 审计日志全量完整性校验
- 超过 1 万条的精确计数
- 翻页超过 1 万条

## 2. 哪些数据会达到 TB 级

平台不保存原始流量。会无限增长的只有两张表：

| 表 | 内容 | 增长来源 |
|----|------|----------|
| `fl_audit_logs` | 审计日志 | 所有操作，至少保留 180 天 |
| `fl_detection_events` | 检测事件 | 检测引擎的发现 |

账号、会话、资产、告警、检测规则等表的数据量在 MB 到 GB 级，不在本文讨论范围内。

## 3. 优化前后对比

测试环境：

- **硬件：** 4 核、15GB 内存、云盘。
- **数据库：** PostgreSQL 16，**全部使用默认配置**（shared_buffers 仅 128MB）。
- **数据分布：** 模拟真实情况。有少数高频用户和大量普通用户；登录约占 50%、告警处置 15%，账号管理等只占 0.5%；约 5% 的记录为失败。

### 3.1 优化前（v0.7.0 表结构，1000 万行，3.6GB）

| 查询 | 耗时 | 原因 |
|------|------|------|
| 首页（最新 50 条） | 586 ms | 每次都要统计全部 1000 万行 |
| 按高频用户 | 818 ms | 同上 |
| 按低频用户 | 496 ms | 沿主键往回扫，过滤掉 200 万行才凑够结果 |
| 某一天 | 921 ms | 过滤掉 494 万行才凑够 50 条 |
| 翻到第 100 页 | 604 ms | 全量计数 |
| 完整性校验 | 9.8 s | 遍历全表 |

这些查询的耗时**都和数据总量成正比**。推算到 TB 级（约 170 倍）会达到 1～3 分钟。

### 3.2 优化后（3000 万行，17.9GB，完全冷缓存）

| 查询 | 首次（冷缓存） | 中位数（热缓存） |
|------|--------------|----------------|
| 首页（最新 50 条） | 6.1 ms | 1.5 ms |
| 按用户：高频用户 | 7.2 ms | 2.3 ms |
| 按用户：普通用户 | 7.6 ms | 1.9 ms |
| 按用户：低频用户 | 4.2 ms | 1.0 ms |
| 事件类别：登录与口令 + 失败 | 5.2 ms | 2.3 ms |
| 事件类别：账号管理（稀有） | 5.9 ms | 2.3 ms |
| 精确事件类型 | 12.4 ms | 7.5 ms |
| 组合：高频用户 + 稀有类别 | 8.1 ms | 1.9 ms |
| 组合：高频用户 + 失败 | 7.5 ms | 3.0 ms |
| 组合：高频用户 + 稀有类别 + 失败 | 4.4 ms | 2.2 ms |
| 组合：稀有类别 + 失败（无匹配） | 3.3 ms | 1.7 ms |
| 组合：类别 + 成功 | 4.5 ms | 2.6 ms |

### 3.3 数据量增加时耗时是否不变

| 查询（热缓存中位数） | 1000 万行 | 3000 万行 |
|------|----------|----------|
| 首页 | 2.2 ms | 1.5 ms |
| 按用户：高频用户 | 7.5 ms | 2.3 ms |
| 按用户：低频用户 | 1.4 ms | 1.0 ms |
| 某一天 | 3.9 ms | 1.5 ms |
| 翻到第 100 页 | 2.8 ms | 2.5 ms |

1000 万行这一列是早期索引版本的结果，3000 万行这一列是最终版本。两列都没有随数据量上升。

## 4. 为什么能推算到 TB 级

### 4.1 设计原则

1. **按月分区：** 查询只扫描时间范围覆盖的分区；过期数据整月删除分区，不再逐行删除。保留 180 天大约是 7 个分区，数据量增长时分区个数不变，只是单个分区变大。
2. **每种筛选组合都有对应索引：** 界面上能组合出来的筛选（用户、事件类别、"只看失败"，以及可选的时间范围），各有一个"等值条件在前、`(time, seq)` 在后"的索引。取一页只需在索引里按顺序读 50 条。
3. **计数封顶：** 最多数到 10001 条，界面上显示为"10000+"。
4. **只读索引就能计数：** 用户名存为独立列（`username_lower`），事件类型和结果附带在索引中（INCLUDE），所有筛选条件都能在索引里判断，计数不用回表。
5. **写入不查大表：** 哈希链的最后一条记录保存在一行的"链头表"里，写入时锁这一行，不需要去大表里找最后一条。写入的时间保证单调递增，按时间排序就等于按序号排序。

索引清单见 `platform/internal/storage/pg_partition.go` 中的 `auditIndexes`。

### 4.2 读页数实测（3000 万行，冷缓存）

| 查询 | 计数读页 | 列表读页 |
|------|---------|---------|
| 无筛选 | 31 | 20 |
| 高频用户 | 86 | 30 |
| 高频用户 + 稀有类别 | 88 | 60 |
| 类别 + 失败 | 74 | 40 |
| 精确类型 | 102 | 56 |
| 类别 + 成功 | 86 | 25 |
| 某一天 | 43 | 6 |

读页数的上限：

- **计数：** 约 10001 ÷ 每个叶子页的条目数（实测约 108）≈ 93 个叶子页，加上每个分区从根往下的几页。
- **列表：** 50 个数据页加上索引页。

两者都**与总行数无关**。唯一会随数据量增长的是 B 树层数：当前每个分区约 500 万行，主索引是 4 层；分区每增大约 100 倍，才多一层。

### 4.3 TB 级估算

| 参数 | 数值 |
|------|------|
| 每行平均占用（含索引） | 约 600 字节（17.9GB ÷ 3000 万行） |
| 1TB 对应行数 | 约 17 亿行 |
| 保留 180 天时每个分区 | 约 2.8 亿行（为当前的 54 倍），B 树多 1 层 |
| 冷缓存每个查询最坏读页数 | 约 102 + 60 + 7 个分区 × 2 次 ≈ 180 页 |

冷缓存耗时约为"读页数 × 单次随机读延迟"：

| 存储介质 | 随机读延迟 | 估算最坏耗时 |
|---------|----------|------------|
| NVMe SSD | 约 0.1 ms | 约 20 ms |
| SATA SSD / 云 SSD | 约 0.2 ms | 约 40 ms |
| 机械硬盘 | 约 8 ms | 约 1.4 s（接近上限，不建议） |

热缓存时，B 树上层节点常驻内存，实际耗时远低于上述估算。

## 5. 做不到 2 秒的操作及处理方式

| 操作 | 数据量增长时 | 处理方式 |
|------|------------|---------|
| 全量完整性校验 | 与总量成正比（实测约 76 万行/秒，17 亿行约 37 分钟） | "校验完整性"按钮改为**增量校验**：从上次检查点往后校验，实测 3.3 ms。全量校验在后台每天自动执行一次，也可手动发起，结果保存并显示在审计页面 |
| 精确计数 | 与匹配数成正比 | 超过 1 万条显示"10000+" |
| 翻页超过 1 万条 | 与偏移量成正比 | 接口拒绝，提示缩小时间范围或增加筛选条件 |
| 导出 CSV | 与导出条数成正比，上限 10 万条 | 实测冷缓存 1.0 秒 |
| 从 v0.7.0 升级 | 一次性迁移，实测每 1000 万行约 2.6 分钟 | 启动时自动在一个事务里完成；数据量大时请安排停机窗口 |
| 未建索引的筛选组合 | 与单个条件的匹配数成正比 | 接口只接受有索引覆盖的筛选条件，"来源"筛选已不再对外开放 |

## 6. 部署要求与配置建议

### 必须满足

- **存储介质：** 使用 SSD（NVMe 最佳）。机械硬盘只能勉强达标。
- **自动清理：** 保持 autovacuum 开启。平台创建分区时已设置 `autovacuum_vacuum_insert_scale_factor = 0.01`，让新写入的数据尽快可以只读索引。如果手动关闭了 autovacuum，计数会退化为回表读取。
- **大批量导入后：** 导入历史数据后执行一次 `VACUUM (ANALYZE) fl_audit_logs`。

### 建议配置（以 64GB 内存的专用数据库服务器为例）

以下是常用的起点，**没有在本次测试中实测**（本次测试全部使用默认配置），需要根据实际负载调整：

```ini
shared_buffers = 16GB
effective_cache_size = 48GB
work_mem = 32MB
maintenance_work_mem = 2GB
random_page_cost = 1.1          # SSD
effective_io_concurrency = 200  # SSD
max_wal_size = 16GB
checkpoint_timeout = 15min
autovacuum_max_workers = 4
```

### 磁盘容量估算

索引占总空间的一半多一点：3000 万行时，表数据约 8GB、索引约 10GB。估算容量时按每行约 600 字节计算，并预留 30% 余量，用于 WAL 和维护操作。

## 7. 复现方法

```bash
# 使用专门的测试库，不要连接生产库（造数会写入大量合成数据）
createdb flowlens_bench
go run ./platform/tools/dbbench -dsn "postgres://.../flowlens_bench" -generate 30000000
psql flowlens_bench -c "VACUUM (ANALYZE) fl_audit_logs"
go run ./platform/tools/dbbench -dsn "postgres://.../flowlens_bench" -bench -verify
```

- **冷缓存测试：** 测试前重启 PostgreSQL，并执行 `sync; echo 3 > /proc/sys/vm/drop_caches`（需要 root 权限）。
- **清理测试：** 加上 `-purge` 会实际删除最早一个月的分区，测试清理耗时。
