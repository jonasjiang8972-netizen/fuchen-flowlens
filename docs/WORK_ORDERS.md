# 拂尘 FlowLens — 工单闭环 (v1.0.0)

> 告警只是线索；只有被分派、处置、复核并留下记录，风险才算真正关闭。

## 一、流程

```
        ┌────────────── 标记误报（需说明理由）──────────────┐
        ▼                                                    │
   待分派 ──开始处理（需负责人）──▶ 处理中 ──提交复核（需处置说明）──▶ 待复核 ──复核通过──▶ 已闭环
   pending                       processing                        review                done
                                    ▲                                 │                    │
                                    └────────驳回（需说明原因）────────┘                    │
                                    └──────────────重新打开（需说明原因，SLA 重新计时）──────┘
```

- **不能跳过复核**：工单只能从"待复核"进入"已闭环"。
- **处置人与复核人分离**：提交复核的人不能自己通过（返回 403 `self_review`）。驳回后提交人被清除，下一个人提交时由别人复核即可。演示模式只有一个模拟用户，不受此限。
- **误报**要写理由，同样可以重新打开；重新打开会把 SLA 重新计时，并把重开次数记在工单上。
- 每次状态变更、分派、备注都进入工单的处理记录，并写入防篡改审计日志（`ticket.create` / `ticket.transition` / `ticket.assign` / `ticket.comment`），记录操作人。

## 二、SLA

| 等级 | 时限 |
|---|---|
| critical | 4 小时 |
| high | 24 小时 |
| medium | 3 天 |
| low | 7 天 |

超过时限为"超时"；已用掉 80% 以上为"临近超时"。时限固定在代码里，尚不可配置。

## 三、自动开单

高危（high）和严重（critical）告警会自动创建工单，建议处置按检测类型给出（例如撞库："封禁来源 IP，通知 IAM 对涉及账号强制改密"）。中低危告警不自动开单，可在告警详情里手动创建。

**同一来源、同一类检测的告警共用一张工单。** 一次撞库跨 30 个账号会产生几十条告警（告警按账号区分），逐条开单会淹没队列。所以第一条告警开单，之后来自同一来源的同类告警作为"关联告警"并入该工单（工单里记录，最多列出 50 条，其余只计数）。

- 上一张工单已**闭环**后，同一来源再出现告警，视为新一轮攻击，开新工单。
- 上一张工单被标为**误报**后，同一来源的后续告警不再开单（分析员已判定无害），告警本身仍保留。
- 没有来源地址的告警各自成单。

## 四、与告警联动

- 工单闭环 → 告警变为 `resolved`；标记误报 → 告警变为 `false_positive`；重新打开 → 告警回到 `in_progress`。
- 在告警上执行**封禁**（见 `docs/SOAR.md`）后，封禁结果（目标和各联动系统的执行情况）会写进该告警对应的未关闭工单。
- 告警详情页有"创建工单 / 查看工单"入口；告警已有未关闭工单时，创建会返回 409 并附带该工单编号。

## 五、API

| 接口 | 权限 | 说明 |
|---|---|---|
| `GET /tickets` | security.read | 参数：`status`、`severity`、`owner`、`alert_id`、`q`（标题/编号/负责人/告警）、`open=true` |
| `GET /tickets/summary` | security.read | 开放数、超时、临近超时、无负责人、按状态计数、近 7 天关闭数、平均闭环小时数、负责人覆盖率 |
| `GET /tickets/{id}` | security.read | 含完整处理记录 |
| `POST /tickets` | alert.handle | 手动开单；带 `alert_id` 时标题、等级、建议处置默认取自告警 |
| `POST /tickets/{id}/transition` | alert.handle | `{to, note, owner}` |
| `POST /tickets/{id}/assign` | alert.handle | `{owner}`，已关闭的工单不能改派 |
| `POST /tickets/{id}/comment` | alert.handle | `{text}` |

状态码：`400` 缺少必填说明或字段无效；`403 self_review` 提交人自己复核；`409 invalid_transition` 状态不能这样变更；`409 ticket_exists` 告警已有未关闭工单（响应里带 `ticket_id`）；`404` 不存在。

## 六、持久化

工单存入 PostgreSQL（文档存储）。用户操作同步写入，失败时回滚并向调用方报错，内存不会领先于数据库；自动开单发生在告警处理路径上，由周期性 flush 落盘，进程异常退出可能丢失最近一次 flush 之后自动创建的工单（对应告警本身仍然存在）。未配置数据库时工单只在内存中。

## 七、已知限制

- 负责人是自由文本（人或团队），没有和账号体系关联，也不做通知（邮件、IM）。
- SLA 时限不可配置，没有工作日历。
- 没有"复发检测"（已闭环风险再次出现时的自动关联）；上面的"新一轮攻击开新工单"是最接近的行为。
- 只有告警来源的自动开单；契约差异、覆盖率盲区等其他治理项还需手动创建。
